## Hypotheses

The useful operation is a programmatically composed semantic judgment with an external result, not a mandatory fixed retrieval pipeline. Direct lookups should remain cheap. Function-level or coherent passage context may beat isolated lines on relationships; longer unrelated state may reduce reliability. Neither claim is guaranteed.

## Initial changes

Keep ask/filter/locate; give TS/JS real declaration ranges. Preserve complete distributions externally and version line refs. Replace lossy printing with explicit atomic rejection and visible cumulative budget, same for read/Jev. Adaptive Jev is default; --require-jev remains a controlled treatment. Log all Jev questions and parsed responses for trace review.

## Adaptive protocol amendments (not preregistered comparisons)

The initial runs mostly skipped Jev. A mandatory single call produced a late confirmation, so an explicit task-level `offload` condition was added. It asks for bulk semantic classification but leaves partitions, question construction and follow-up reads to the root. Output budgets of 4,000 and 8,000 characters test pressure separately from the initial 16,000. Conditions with different budgets or harness versions are not paired causal estimates.

A new 16-case fixture was authored with gold before its first run, covering stale validation, post-test edits, partial suites, skips, quoted sample output, running jobs, and suite scope. This is development-time follow-up, not a sealed benchmark holdout after the subsequent iterations.

A discovered source-via-error side channel is fixed by charging error details to the same budget. A binding probe replays an actual failed Jev request with only explicit record targeting added, twice per condition. The final API rejects exact duplicate question definitions over shared material before sending them. All intermediate runs and failures remain recorded.
