# SOCO：原型迭代与真实轨迹审查

这轮证明了一个有限但有用的机制：root 能用代码把外部材料变成一批局部语义判断，让 Jev 执行，只把结果和少量原文带回上下文。还没有证明它会自动选择这种策略、稳定节省总成本，或者完整替代直接阅读。

实现位于本项目。原始运行在忽略的 `runs/`，逐次指标见 [results.json](results.json)，判断器探针见 [probes.json](probes.json)。`completed` 仅表示交卷，不代表任务正确或完整。以下所有准确性数字均为检查答案后的结果。

## 研究依据与设计取舍

参考了 Prime Agent 在 `cd1f215cffd09223316c54dddae5e1b654718c31` 的 [RLM prompt](https://github.com/PrimeIntellect-ai/prime-agent/blob/cd1f215cffd09223316c54dddae5e1b654718c31/packages/coding-agent/src/core/prompts/rlm.ts) 和 [runtime 文档](https://github.com/PrimeIntellect-ai/prime-agent/blob/cd1f215cffd09223316c54dddae5e1b654718c31/packages/coding-agent/docs/rlm-runtime.md)。可借鉴的是持久代码环境、外置中间结果、宿主管理调用生命周期，以及已知小查询直接处理的原则。SOCO 保留 TypeScript 宿主和 JavaScript REPL，没有照搬它的 Python kernel、daemon 或多 agent 系统。

Jev 官方明确列出间接推理、数值/时间、干扰内容等弱点。当前文档给 Jev 1.13 的限制是总请求 64k tokens，state 加最长 question 32k tokens；输入 $0.042/M，输出免费。SOCO 的 **24 KB 请求上限是本地实现限制**，本轮没有验证 Jev 接近官方上下文上限时的表现。[官方模型文档](https://docs.typesafe.ai/models)、[已知局限](https://docs.typesafe.ai/model-jaggedness/jev-1.13)（2026-09-26 UTC 查阅）。

目前最合适的三个起点：

- 已知名字或字面量：直接 search/read，不要求 Jev 介入。
- 大量独立记录：代码分批，逐记录构造有明确目标的 Noul，外置保存完整分布，回传紧凑结果；检查疑难项，也抽查负例。
- 少数相关函数：连同必要定义给 Jev 判断具体假设，再读决定性的原文。不要把孤立一行当成完整证据。

`ask/filter/locate` 已足够表达这些策略。这轮没有扩展大量细碎动作，也没有固定检索顺序。`--require-jev` 作为实验开关保留；默认仍允许跳过 Jev。另有实验脚本的 `offload` 条件，明确要求委托批量判断，但问题、分批和调查顺序仍由 root 编程决定。

## 实现修复

1. 原先每个 cell 的局部变量消失，导致 root 定义的 helper 下一步不可用。改成真正持久的 Node REPL，支持 top-level await；处理了 REPL 通过 domain 报错而不回调造成的挂起。`var` 或 `state` 适合重用；`const/let` 重声明仍遵循 JavaScript 规则。
2. 输出预算现在跨整个调查累计，与 read baseline 一致。超额的打印整体拒绝，原对象仍在环境中。源代码打印去掉重复 hash 元数据；保留路径和行号。错误详情也计费，堵住实际观察到的 `throw Error(source)` 绕过。
3. TS/JS symbol 使用 AST 提供完整声明范围；其他语言仍是声明行回退。窗口最多 400 行，加载不自动打印。行引用携带版本 hash，改动后的旧引用拒绝读取。`window/lines/read` 都计入源读取统计。
4. 完整概率分布留在外部状态，不再过早截为 top 4。记录 ask 的材料、问题和解析结果。失败运行保留 trace 和已知用量，未知费用不当作零。
5. 拦截同一共享材料下完全重复的问题定义。输出 ID 不能替代 instructions 中的目标绑定，错误会在花费 Jev 请求前返回。

这些预算控制是研究用的输出通道约束；本地子进程不是安全沙箱。系统提示、生成代码、状态元数据也占 root context，报告另外统计总 root tokens，不能把打印字符数当作全部推理成本。

## 数据与比较条件

root 为 xAI `grok-4.7`；14 次 root 调用、至多 24 个 Jev 请求、每 cell 最多 6,000 字符。记录 provider usage、cache 和 SDK 成本估计。不同预算、提示和 harness 版本是迭代实验，不能合并成统一 A/B 结论。并发请求、缓存和单次波动也使端到端延迟不适合做速度倍数宣称。

- Booking：已有小型跨文件因果任务，适合作为回归。
- HTTPX：公开项目 0.28.1，commit `26d48e0634e6ee9cdc0533996db289ce4b430177`；追踪重定向 method/body/Authorization/Host/Cookie。代码只读，不执行第三方项目。已知公开代码可能有预训练污染。
- Episodes：48 条合成 trace，51,192 bytes，20 个阳性，12 种模板重复。语义信息比总字节数少得多，好的正则也能解决，不能当真实长轨迹 benchmark。
- 新案例集：16 条不同场景，8 个阳性；加入测试后改代码、旧版本验证、只跑 smoke、全部 skip、引用日志与真实执行、运行中未完成等。gold 在首次运行前写好并放在 corpus 外。它仍是合成开发集，不是不可触碰的测试集。

|---|---:|---|---:|---:|
| 48 条，read adaptive #1 | 16k | 20/20 阳性，无误报 | 0 | $0.07843 |
| 48 条，Jev adaptive #1 | 16k | 同样全部正确，但完全没用 Jev | 0 | $0.11998 |
| 48 条，required #3 | 16k | 全部正确；主要读完后才让 Jev 确认重复模式 | 1 | $0.07483 |
| 48 条，Jev adaptive #4 | 4k | 步数耗尽，没调用 Jev | 0 | $0.09512 |
| 48 条，offload #5 | 4k | 20/20，无误报；大多数为未逐项核实的预测 | 3 | $0.03347 |
| 48 条，offload #6 | 4k | 仅处理 8 条后声明未完成 | 1 | $0.04252 |
| 48 条，offload #7 | 8k | 20/20，无误报；引用行号整体偏一行 | 3 | $0.10227 |
| 新 16 条，offload #6 | 4k | 16 个语义判断全部正确；输出省略 episode- 前缀 | 1 | $0.07025 |
| 新 16 条，read #7 | 8k | 找到 6/8 阳性，无误报，明确承认未读完 | 0 | $0.04085 |
| 新 16 条，offload #7 | 8k | 最终 8/8，但 Jev 问题未绑定记录，root 改用原文救回 | 1 | $0.05574 |
| 新 16 条，最终 harness #8 | 8k | Jev 16 条全对；最终列表只交 3 个已核实阳性，其余放在说明中标为预测，任务未完整交付 | 1 | $0.07207 |

48 条 offload #5 是最清楚的一次机制演示：root 先检查一条例子的格式，在代码里抽取各条的 observation/final 等相关文本，构造独立问题并分成 3 批。只有正例 ID 与概率返回。Jev 共 10,672 输入 tokens，约 $0.000448，累计请求约 0.53 秒。总 root 输入（含缓存读取）24,368 tokens，输出 1,349 tokens；打印 3,992 字符。但没有预算逐项核实或审计所有负例，最终明确称其为预测。不能把标签全对解释成已经完成证据审查。

新 16 条 offload #7 则说明，最终答案正确并不代表 Jev 起了作用。它的 16 个问题 instructions 完全相同，只是输出键不同。分数全在 0.67–0.76，root 发现没有区分度后打印各记录的原文，自己判对。这次成功是 fallback 的价值，不能算 offloading 成功。

HTTPX 的两个 #4 运行都没有使用 Jev。Jev-enabled 的回答正确说明了 POST 重写、流和两个 body headers、Authorization 例外、Host 和 raw Cookie，但对 jar 后续应用主动保留不确定性；read 回答把 Host 错说成总是 pop 后重建，遗漏明确的两个 body headers，且补充了没有充分读到的 cookie 行为。早期 #1 还出现预算耗尽或实质弃答。这里没有 Jev 收益证据，主要暴露 root 的预算管理和证据约束问题。

Booking adaptive #2 用 7 步直接读完，没调用 Jev，核心机制正确。这个结果符合“已知小范围直接读”的预期。

另有两类必须保留的失败：required #2 遇到 REPL 错误回调挂起，随后 API timeout；修复后有回归测试。read #4 虽找出 16/20，但大量源文被放入 Error 消息绕过预算，属于**预算不合规运行**，不参与公平比较。旧 booking 报告把 `booking.ts:16` 说成未打印也不对：原始 trace 的 BOOK 段确实包含它，已更正文档。

## 关键对照：问题必须绑定对象

从新案例 offload #7 原始请求直接重放，固定材料、规则和模型，只改变 instructions 是否加 `Judge only record material.e101.`，每组重复两次。

| 条件 | 0.5 阈值结果 | 典型分数 |
|---|---|---|
| 未绑定：16 个相同问题 | 两次均把 16 条全判正，8 个误报 | 0.68–0.76 |
| 明确绑定每条记录 | 两次均 8 真阳性、8 真阴性 | 阳性 0.94–0.98；阴性 0.02–0.41 |

这支持的是“共享 state 下明确指向记录很重要”，不是证明完整系统稳定。接口的新 guard 只捕捉完全重复的定义，不能自动验证所有自然语言问题是否充分、明确或正确。

## 粒度探针：保留证据比追求最细更重要

固定 booking 的 6 个命题，分别给孤立关键行、相关函数段、四个完整小文件、相关段加 HTTPX 无关代码，每组两次，共 8 个请求。

- 孤立行缺少定义和函数体。`compare_seconds` 两次仅 0.46；但复合因果判断仍给 0.77，说明缺证据不一定导致低分，不能用概率当证据充分性的证书。
- 连贯函数段的 `compare_seconds` 为 0.95–0.96，单位错误为 0.83–0.88；支持先保留必要上下文。
- 完整小文件与加干扰组没有稳定明显退化。这次数据**不支持**“稍长就必然坏”的结论。
- 最大材料约 16.7k JSON 字符，很多还是引用元数据，不是 32k tokens；未测真正超长 context。
- 与旧 booking 的低分相比，问题措辞也不同，不能把改进全部归功于粒度。

## 当前判断

范式值得继续，最有证据的部分是代码生成的 **semantic map + 外置结果 + 自适应读取**。粒度可以先选一个语义完整的记录/函数，由代码便宜地剥离格式噪声，关系跨函数时补足依赖。不是越细越好，也不是必须让 Jev 遍历每个文件。

瓶颈目前更像调用策略与信息接口：root 会跳过工具、重复打印索引、忘记绑定问题、花光审计预算；最终会出现准确标签但错误引用，或正确答案实际上全部由 root 阅读得到。便宜的判别器已经能支撑部分批量判断，但还没有稳定转化为系统总成本优势。

后续最有价值的是固定当前接口，在更自然、多样的公开轨迹上测完整率、误漏报、证据引用和总成本，并加入精简 deterministic baseline；随后才考虑学习何时 offload 的 policy。不能用单次漂亮结果或单次失败代替这个比较。

## 最终验证与交付边界

最终实现通过 **23/23 自动化测试**，包括持久变量/错误恢复、累计预算、错误泄漏、源版本、完整分布以及共享问题绑定约束。`git diff --check` 和 CLI help 通过。共记录 19 次真实 root 运行与 12 次独立 Jev 探针，含失败和不同开发版本；它们不是 19 个同分布 benchmark 样本。API 记录的已知成本合计约 $1.38，含 Jev 估计；一条失败运行用量可能不完整，不能视为账单。

最终 harness 的 #8 运行已经明确绑定 16 个问题，Jev 原始预测 8 真阳性、8 真阴性。root 却继续花预算逐条阅读，最后把 3 条已核实阳性放入主列表，把其余 5 条正确阳性留在说明中标为未核实。这是一次不完整交付，不应美化为任务成功。它说明下一步应把“批量预测结果”“已核实证据”“尚未核实项”的输出契约分清楚，否则要求 root 重读每条才能接受结果，会抵消 offloading。

当前交付的是可运行、可测量、能复现成功和失败机制的研究原型。判断器能力、接口语义和 root 调查策略已经可以分开定位；它还不是一个自动稳定省钱的成熟 agent。
